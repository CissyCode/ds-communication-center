# 조간 지면 스크랩 자동화 검토안 (초안)

> 목표: 아침에 PC 설치형 스크랩마스터를 열면 **검토용 그룹에 후보 기사가 선택·정렬된 초안**이 준비돼 있는 상태.
> 자동 배포·최종 PDF 생성·확정 스크랩 수정은 범위 밖입니다. 최종 포함·제외·순서는 사람이 결정합니다.

이 문서는 설치본 확인 전에 쓴 초안입니다. 스크랩마스터의 실제 기능은 아래 1장에서 확인한 뒤 설계를 확정합니다.
공개 자료에서 확인되는 것은 제공사가 (주)다하미커뮤니케이션즈이고, 모바일판 소개에 키워드 검색·자동 스크랩·PC/웹과의 스크랩 공유가 있다는 정도입니다.
PC 설치본의 자동검색 조건, 그룹 관리, 순서 변경, 내보내기, 연계 기능은 **확인이 필요한 미확인 사항**으로 둡니다.

---

## 0. 설계 원칙

| 원칙 | 내용 |
|---|---|
| 공식 기능 우선 | 자동검색·자동스크랩·그룹·순서·내보내기는 제품 기능으로 먼저 해결합니다. 다음으로 제조사가 제공하는 연계 기능(내보내기/가져오기, 공식 API 등)을 씁니다. 그래도 안 되는 동작만 **승인된 화면 자동화(RPA)** 로 보완합니다. |
| 금지 전제 | 비공개 내부 통신 분석, 로컬 DB·저장 파일 직접 수정, 인증 우회는 하지 않습니다. |
| 쓰기 범위 제한 | 자동 작업이 쓰는 곳은 `자동검토_YYYYMMDD` 같은 **전용 검토 그룹 하나**뿐입니다. 확정 그룹, 다른 사용자 그룹, 과거 스크랩은 읽기 전용입니다. |
| 판단과 실행 분리 | "무엇을 몇 번째에 둘지" 판단하는 엔진은 스크랩마스터 밖에서 규칙과 예시로 돌립니다. 스크랩마스터에서는 그 결과를 담고 정렬만 합니다. |
| 기록 우선 | 실행 단계와 신문별 상태, 추가한 기사를 모두 원장(ledger)에 남깁니다. 재실행·중단 복구·중복 방지가 모두 이 원장을 기준으로 돌아갑니다. |
| 학습보다 규칙 | 처음에는 편집 규칙, 현안 목록, 과거 예시로 시작합니다. 모델 학습은 실제 검토 결과(명시적 제외 포함)가 충분히 쌓인 뒤에 따로 판단합니다. |

## 1. 실제 설치본에서 확인할 항목

결과를 아래 표의 "판정" 칸에 **공식 지원 / 우회 가능(RPA) / 불가** 로 적어 주세요. 이 판정에 따라 연동 방식이 정해집니다.

### 1-1. 계약·환경

| # | 확인 항목 | 왜 필요한가 | 판정 |
|---|---|---|---|
| E1 | 설치 버전, 라이선스 단위(PC·사용자 수), 계약 매체 목록 | 대상 신문과 자동화 PC 범위 | |
| E2 | 계약상 기사 제목·본문·지면 이미지를 **사내 PC의 별도 프로그램에서 분석·보관**해도 되는지 | 선정 엔진이 기사 텍스트를 읽을 수 있는지가 이 답에 달려 있습니다 | |

### 1-2. 수집·검색

| # | 확인 항목 | 확인 방법 | 판정 |
|---|---|---|---|
| S1 | 자동검색(자동스크랩) 조건 표현력: AND/OR/제외어, 구문 검색, 매체 지정, 면 지정, 기간 | 테스트 키워드 2~3개로 실제 설정 | |
| S2 | 자동검색 스케줄 실행 여부와 시각 지정, 결과가 저장되는 위치(그룹·폴더·목록) | 설정 화면, 다음 날 결과 확인 | |
| S3 | **지면 기사와 온라인 기사 구분**이 화면·내보내기에서 보이는지 | 같은 키워드로 양쪽 결과 비교 | |
| S4 | 기사별 메타데이터: 발행일, 매체, 면수, **판(초판/재판/종판) 정보**, 섹션, 기자, 기사 고유 ID | 기사 상세, 목록 컬럼, 내보내기 파일 | |
| S5 | 신문별 "수집 완료/미수집" 상태 표시(업데이트 시각, 미발행 표시) | 이른 새벽과 정상 시각에 각각 확인 | |
| S6 | 검색 결과 0건과 오류/미수집이 화면상 구분되는지 | 존재하지 않는 키워드 검색 vs 미수집 매체 검색 | |

### 1-3. 그룹·순서·내보내기

| # | 확인 항목 | 확인 방법 | 판정 |
|---|---|---|---|
| G1 | 사용자 그룹(폴더) 생성·이름 지정, 그룹 간 복사/이동 | 테스트 그룹 생성 | |
| G2 | 그룹 안 순서 변경 방식: 드래그, 위/아래 버튼, 번호 입력, 정렬 기준 | 실제 조작 | |
| G3 | 그룹 내용을 **목록 파일로 내보내기**(Excel/CSV 등): 어떤 컬럼이 나오는지, 기사 ID가 포함되는지 | 내보낸 파일 확인 | |
| G4 | **목록 가져오기**(기사 ID 목록으로 그룹 채우기) 기능 유무 | 메뉴·매뉴얼·제조사 문의 | |
| G5 | 그룹이 다른 사용자/PC/웹과 동기화되는지(검토 그룹이 남에게 보이는지) | 다른 PC에서 확인 | |
| G6 | 작업 이력·로그 제공 여부 | 메뉴·매뉴얼 | |

### 1-4. 화면 자동화 적합성 (공식 기능으로 안 되는 부분이 있을 때만)

| # | 확인 항목 | 왜 필요한가 |
|---|---|---|
| R1 | 컨트롤이 Windows UI Automation으로 식별되는지(이미지 인식에만 의존하면 깨지기 쉬움) | 안정성 |
| R2 | 키보드 단축키 지원(검색, 그룹 추가, 순서 이동) | 클릭 좌표 의존 줄이기 |
| R3 | 현재 선택된 그룹 이름과 목록 건수를 화면에서 읽을 수 있는지 | 쓰기 전 "올바른 그룹인지" 검증 |
| R4 | 업데이트 팝업, 로그인 만료, 공지창 같은 방해 요소 | 예외 처리 |

### 1-5. 제조사에 문의할 질문

1. PC 설치본에 공식 API, 명령줄 옵션, 연계 모듈(기사 목록 조회, 그룹 추가, 순서 지정)이 있습니까?
2. 그룹 목록을 기사 ID 포함 파일로 내보내고, 같은 형식으로 다시 가져올 수 있습니까?
3. 기사 메타데이터에 판 정보와 지면/온라인 구분이 포함됩니까?
4. 신문별 수집 완료 여부를 프로그램에서 확인하는 공식 방법이 있습니까?
5. 계약 범위 안에서 기사 텍스트를 사내 분석 도구로 처리할 때 제약은 무엇입니까?

> **판정에 따른 연동 방식 (예상 시나리오)**
> - **A안 (G3·G4 지원):** 자동검색 결과 내보내기 → 외부 엔진 선정·정렬 → 가져오기로 검토 그룹 생성. RPA가 거의 필요 없습니다.
> - **B안 (G3만 지원):** 내보내기 → 외부 엔진 → RPA가 기사 ID/제목으로 찾아 검토 그룹에 담고 순서 조정.
> - **C안 (내보내기 불가):** 화면에서 목록 읽기까지 RPA가 맡아야 합니다. 취약하고 계약 확인(E2)이 더 중요해집니다. 시험 범위를 줄이는 것을 권합니다.

| 대상 신문 목록 | 매체 등급 구분(종합지/경제지/전문지 등)이 있으면 함께 | 매체 우선순위 |

| 묶음 표시 | 분석 시 부여 | 같은 사안의 여러 매체 보도를 한 덩어리로 배치했는지 |

### 2-3. 분석 방법

**(1) 선정 기준과 배열 기준은 따로 분석합니다.**

- **선정:** 어떤 기사가 들어갔는가. 매체, 면수, 주제, 당사 관련성, 키워드 일치 유형(제목/본문)을 봅니다.
- **배열:** 들어간 기사들이 어떤 순서로 놓였는가. 섹션 순서, 섹션 안 정렬 키(관련성 → 매체 등급 → 면수 등), 같은 사안 묶음 처리를 봅니다.

**(2) 완성본에 없는 기사를 '제외 대상'으로 쓰지 않습니다.**

- 완성본은 **포함된 예시(positive)** 만 확실한 정보입니다.
- 빠진 기사는 검토 후 제외했는지, 아예 못 봤는지 알 수 없으므로 **라벨 없음(unlabeled)** 으로 둡니다.
- 명시적 제외(negative)는 운영 단계에서 사람이 **검토 그룹에서 직접 뺀 기사**만 인정합니다(4장).
- 같은 날 자동검색 원본이 있으면 "후보 풀에는 있었는데 완성본에 없음" 정도는 볼 수 있습니다. 그래도 담당자가 원본 목록을 매번 끝까지 본다고 확인되기 전까지는 **약한 참고 정보**로만 씁니다.
- 그래서 과거 자료로 측정할 수 있는 것은 **재현율(완성본 기사를 후보가 얼마나 잡았는가)과 배열 일치도**입니다. 정밀도는 운영 시험에서 사람이 평가해야 합니다.

**(3) 일반 순서와 예외 순서를 구분합니다.**

1. 40~60일치에서 섹션 순서와 섹션 안 정렬 키를 추정해 **기본 배열 규칙**을 만듭니다.
2. 기본 규칙을 과거 각 날짜에 적용했을 때 실제 순서와 크게 어긋나는 날·기사를 **예외 후보**로 뽑습니다.
3. 예외 후보 중 10~15건 정도를 담당자에게 보여 주고 사유를 표시받습니다. 예: 현안 최상단 배치, 당일 보도자료 반영, 오보 대응, 임원 동정.
4. 사유가 "현안"이면 상시 규칙이 아니라 **기간이 있는 현안 규칙**으로 분리합니다.

**(4) 중복 보도 처리 패턴을 기록합니다.**

같은 사안을 여러 매체가 썼을 때 처리 방식을 날짜별로 기록합니다. 전부 넣는지, 대표 1~2건만 넣는지, 묶어서 연속 배치하는지 같은 것입니다.

## 3. 핵심 동작 설계 (필수 조건 대응)

### 3-1. 기사 식별 키와 원장

```
article_key = 기사 고유 ID (제공되면)
            | 없으면: 발행일 + 매체 + 지면/온라인 + 면수 + 정규화 제목 해시
```

원장 테이블은 스크랩마스터 저장 파일이 아니라 **자동화 도구 쪽의 별도 파일/DB**에 둡니다.

| 테이블 | 주요 컬럼 |
|---|---|
| `run` | run_id, 대상 일자, 시작/종료 시각, 규칙 버전, 현안 버전, 전체 상태 |
| `paper_status` | run_id, 매체, 상태, 확인 시각, 결과 건수, 오류 메시지, 화면 증적 경로 |
| `candidate` | run_id, article_key, 매체, 발행일, 면, 판, 지면/온라인, 제목, 점수, 선정 사유, 추천 순번, 중복 묶음 ID |
| `action` | run_id, article_key, 단계(검색/선정/담기/정렬), 결과, 시각 |
| `review_diff` | 일자, article_key, 사람이 한 일(추가/제외/이동), 이전·이후 순번, 사유 코드(선택) |

### 3-2. 필수 조건별 처리

| 조건 | 처리 |
|---|---|
| 온라인/지면 구분 | 기본 대상은 지면만. 구분 정보가 없는 기사는 자동 선정하지 않고 "확인 필요"로 표시 |
| 발행일·매체·면수·판 유지 | 원장에 원문 표기 그대로 저장. 검토 그룹 안에서도 제목 옆에 보이도록 구성 가능한지는 G2·G3 결과에 따름 |
| 초판·종판 중복 | **같은 매체·같은 발행일**이고 제목·본문 유사도가 높으면 같은 묶음으로 보고 최신 판 1건만 담음. 나머지는 원장에 "판 중복"으로 연결 |
| 유사 기사 | **다른 매체**의 같은 사안은 자동 삭제하지 않음. 같은 묶음 ID만 붙여 연속 배치를 추천하고, 대표 외 기사는 "중복 가능" 표시 |
| 다른 취재 내용 보존 | 같은 매체 안이라도 유사도가 애매한 구간(기준값 근처)은 묶지 않고 둘 다 담음. 잘못 지우는 것보다 하나 더 보이는 쪽을 택함 |
| 결과 없음 vs 수집 실패 | 신문별 상태를 `미수집`, `수집됨-결과있음`, `수집됨-결과0건`, `실패`, `휴간` 으로 구분. `결과0건`은 검색이 정상 수행됐다는 증적(건수 표시 화면 등)이 있을 때만 인정. 증적이 없으면 `실패` |
| 일부 미수집 시 미완료 | 모든 대상 신문이 `결과있음`/`결과0건`/`휴간`일 때만 전체 `완료`. 하나라도 `미수집`/`실패`면 `부분 완료(N/M)`로 표시하고 검토 그룹 이름이나 첫 항목에 그 사실을 남김 |
| 재실행 시 중복 금지 | 담기 전에 ① 원장의 `action`에서 같은 run 일자·article_key의 `담기 성공` 기록, ② 가능하면 검토 그룹의 현재 목록을 함께 확인. 둘 중 하나라도 있으면 건너뜀 |
| 확정본·수동 작업 보존 | 자동화는 전용 검토 그룹만 씀. 쓰기 전에 화면의 현재 그룹 이름을 확인하고 다르면 즉시 중단. 사람이 이미 검토 그룹을 손댔으면(원장에 없는 기사가 있거나 순서가 바뀜) **재정렬하지 않고 추가만** 함 |
| 중단 시 진행 확인 | 단계마다 `action`에 기록. 재실행하면 마지막 성공 지점부터 이어서 진행. 아침에 "신문별 상태 + 담은 건수 + 실패 목록" 요약을 한 화면이나 파일로 보여 줌 |

### 3-3. 규칙의 3층 구조

|---|---|---|

## 4. 운영 중 개선 (사람 수정의 기록과 반영)

1. 매일 검토가 끝난 뒤 검토 그룹(또는 확정 그룹)의 최종 목록을 읽어 추천안과 비교하고 `review_diff`에 기록합니다. 확정 그룹은 **읽기만** 합니다.
   - **추가:** 추천에 없던 기사를 사람이 넣음 → 키워드 누락 또는 선정 기준 부족 후보
   - **제외:** 추천했는데 사람이 뺌 → **명시적 제외 예시**(검토 후 뺀 것이 확실함)
   - **이동:** 순번 차이 → 배열 규칙 또는 현안 규칙 후보
2. 사유 코드는 선택 입력으로, 최소한만 둡니다(예: 현안 / 관련성 낮음 / 중복 / 매체 / 기타).
3. **규칙은 자동으로 바뀌지 않습니다.** 주 1회 리포트로 "같은 유형의 수정이 N회 이상 반복된 항목"만 규칙 변경 **제안**으로 올리고, 담당자가 승인한 것만 반영합니다.
4. 현안 사유로 한 수정은 상시 규칙 제안에서 빼고 현안 규칙 쪽으로 보냅니다.
5. 명시적 제외와 이동 기록이 수백 건 이상 쌓이면 그때 학습 모델을 비교 대상으로 추가할지 판단합니다.

## 5. 가장 작은 시험 범위 (Phase 0 → 1)

### Phase 0 — 설치본 확인과 자료 확보 (1주)

- 1장 체크리스트 작성, 제조사 질의 발송, 계약·보안 확인(E2·E3)
- 2장 자료 확보, 담당자 인터뷰
- **산출물:** 연동 방식 판정(A/B/C안), 분석용 과거 데이터셋

### Phase 1 — 추천만 하는 비교 시험 (스크랩마스터에 쓰지 않음)

| 항목 | 범위 |
|---|---|
| 대상 신문 | **4개** (종합지 2, 경제지 2). 수집 시각이 안정적인 매체 위주 |
| 키워드 | 상시 키워드 전체 + 당시 현안 **1~2개** |
| 기간 | 과거 백테스트 **20 영업일** + 실시간 섀도 운영 **10 영업일** |
| 출력 | 스크랩마스터 밖의 **추천 목록 파일**(Excel): 순번, 섹션, 매체, 면, 판, 제목, 점수, 선정 사유, 중복 묶음, 신문별 수집 상태 |
| 사람의 일 | 평소대로 스크랩 작성. 섀도 기간에는 추천 목록 중 완성본에 없던 기사에만 "넣을 만함 / 아님"을 표시(하루 5분 이내) |

**측정 지표** (목표값은 시험 전 담당자와 합의할 제안치입니다)

| 지표 | 정의 | 제안 목표 |
|---|---|---|
| 재현율 | 완성본(4개 매체 범위) 기사 중 추천 목록에 있는 비율 | 90% 이상 |
| 상위 정밀도 | 추천 상위 N건 중 완성본 포함 + 사람이 "넣을 만함"으로 표시한 비율 | 70% 이상 |
| 섹션 일치 | 완성본 기사가 같은 섹션으로 분류된 비율 | 90% 이상 |
| 배열 일치 | 섹션 안 순서 일치도(순위 상관), 완성본으로 맞추는 데 필요한 이동 횟수 | 날짜별 추이로 판단 |
| 상태 정확도 | 신문별 `결과0건`/`실패`/`미수집` 판정이 실제와 맞는 비율 | 100% |
| 중복 처리 오류 | 다른 취재 기사를 잘못 묶은 건수 | 0건 |

### Phase 2 — 검토 그룹에 담기 (선정 자동화)

- 조건: Phase 1 지표 충족, 연동 방식 확정
- 전용 검토 그룹에 **담기만** 하고 순서는 건드리지 않음
- 재실행·중단 복구·부분 완료 표시를 의도적으로 시험(실행 중 강제 종료, 같은 날 두 번 실행, 매체 하나를 미수집 상태로 둔 실행)

### Phase 3 — 배열까지 자동화

- 검토 그룹 안 추천 순서 적용, 대상 신문 전체로 확대
- 사람이 손댄 그룹은 재정렬하지 않는 보호 규칙 확인
